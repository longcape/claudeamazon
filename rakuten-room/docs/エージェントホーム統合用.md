## ■ 問題点

### 【最重要】楽天APIを一度も叩いていない

全検証がフィクスチャベース。実データで壊れうる箇所は `HANDOFF.md` §4 に
優先度順で列挙済み。ローカル移行後、最初に潰すこと。

対策として `node bin/room.js probe` を実装済み。30件取得して各フィールドの
充足率を出し、欠損があれば影響を名指しする。

### 【要確認】ジャンルIDの実在未確認

`config/strategy.json` の以下はサンプル値であり、実在確認をしていない。

```
rootGenreId:      100938（インテリア・寝具・収納）… 確度は高いが要確認
relatedGenreIds:  100804, 558929               … 特に 558929 は確度が低い
```

`node bin/room.js genre 0` で確認できる。
**そもそもこのジャンル自体がサンプルで、運用者の実際の商材に置き換える前提。**

### 【暫定実装】楽天ROOMの内部スコアは読めないため代理指標で代用

楽天ROOMのCV誘導・閲覧誘導・外部送客スコアは外部から取得不可。
以下の代理指標を運用者の手入力から算出している。

| ROOMの隠しスコア | 代理指標 |
| --- | --- |
| 閲覧誘導スコア | クリック ÷ いいね |
| CV誘導スコア | 成約 ÷ クリック |
| 外部送客スコア | 送客投稿のクリック比 |

### 【暫定実装】広告出稿量は非公開のため痕跡から推定

楽天は広告出稿量を公開しない。アフィリ報酬率の引き上げ・ポイント倍率・
クーポン・別キーワードでの上位再出現・ランキング掲載を「販促投資の痕跡」として
積み上げ、広告加熱度を推定している。直接の広告データではない。

### 【暫定実装】投稿実行が手動

楽天ROOMに公開の投稿APIが無いため。§「最新決定事項」参照。

### 【修正済み】このセッションで発見・対処した不具合

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| 売上投稿が末尾で連続した | パターン列を頭から消費する方式 | ペア確定方式に作り直し |
| 90商品が10商品に潰れた | 重複排除の指紋が商品名の先頭14文字のみ | 商品名の数値も指紋に混ぜた |
| 30枠中21枠しか埋まらない | 1ショップ3商品上限 × 候補ショップ数不足 | 原因を名指しで警告 |
| 日中の投稿枠が空振り | ペアが1枠スロットに入らずbreak | 先読みで単発投稿を回す |
| 20:00前に投稿が入った | ゆらぎがゴールデンタイム外へはみ出した | 内側にクランプ |
| 保存容器が「伸縮」商品として売られた | 説明文の宣伝文句を拾っていた | 商品名の一致を優先 |
| 商品説明・報酬率が欠落しうる | 検索APIの `field=1`（一部情報のみ）指定 | `field=0`（全情報）に修正 |
| テストが実設定ファイルを汚染 | trend の書き込み先がリポジトリ直下固定 | `ROOM_CONFIG_DIR` を導入。混入データ削除（2794行→24行） |

## ■ 最新決定事項

このチャットで確定した方針。**過去の計画書より、こちらを優先すること。**

1. **投稿の実行は手動とする（自動投稿しない）**
   楽天ROOMに公開の投稿APIが無く、ブラウザ操作による無人投稿は規約に抵触しうる。
   アカウント停止のリスクを負わない。エンジンは「いつ・何を・どの文で出すか」を
   確定させたキューまでを成果物とし、投稿の実行のみ `src/post/adapters/` で差し替える。
   既定は台本を出すだけの `manual` アダプタ。

2. **開発・運用ともローカルに全面移行する**
   理由: ① `data/` がコンテナ回収で消えると売上速度が永久に未計測になる
   ② cron が必要 ③ `.env` の置き場 ④ 投稿が手元で起きる
   ⑤ ZIP取得のためクラウド側とファイルが繋がらず、両方編集すると食い違う。
   **移行完了後、クラウドセッションではコードを変更しない。**

3. **運用者はターミナル操作に不慣れ**
   コマンドは運用者に打たせず、AI側で実行する。運用者に依頼するのは
   ブラウザ操作（楽天ID取得）、楽天ROOMへの貼り付け、実績数値の報告のみ。
   専門用語には短い言い換えを添える。`CLAUDE.md` に明記済み。

4. **初動30件は collect を3日以上回してから組む**
   売上速度がスナップショットの日次差分のため、初日は全商品が未計測扱いになる。
   アルゴリズムが最初の30件を極端に重く評価する以上、ここを急がない。

5. **1ジャンルに集中する**
   ジャンル分散はアルゴリズム評価を落とす。複数ジャンル運用は当面着手しない。

6. **紹介文は「誰の・どんな悩みが・どう変わるか」を必須とする**
   欠けた場合はNG検査が計画ごと停止する。

| ファイル | 理由 |

## 2. 起動方法

**前提**: Node.js 18以上。依存パッケージなし（`npm install` 不要）。

```bash
cd rakuten-room
cp .env.example .env      # RAKUTEN_APP_ID と RAKUTEN_AFFILIATE_ID を記入
```

| コマンド | 内容 |
| --- | --- |
| `npm test` | テスト29件 |
| `node bin/room.js doctor` | 設定と接続の確認 |
| `node bin/room.js probe [keyword]` | 実データの充足率を点検 |
| `node bin/room.js genre [id]` | ジャンルIDを調べる |
| `node bin/room.js collect` | 候補収集（毎日／約3分） |
| `node bin/room.js daily` | 収集＋計画作成（cron向け） |
| `node bin/room.js launch` | 初動30件の計画 |
| `node bin/room.js plan --days=3` | 通常運用の計画 |
| `node bin/room.js next` | これから出す投稿を見る |
| `node bin/room.js now` | 投稿時刻が来たものを出す |
| `node bin/room.js done 1,2,3` | 投稿済みにする |
| `node bin/room.js record 1 --clicks=30 --cv=1 --likes=12 --revenue=2480` | 実績記録 |
| `node bin/room.js report` | 隠しスコアの代理指標 |
| `node bin/room.js trend` | 上昇ワードの候補 |

**環境変数**

| 変数 | 必須 | 内容 |
| --- | --- | --- |

## 5. 前提知識 — 楽天ROOM運用の設計方針

次に入るAIが判断を誤らないよう、設計の背景を残す。

- **商品選定は楽天ROOMではなく楽天市場を参照する。** ROOM内の人気は後追い情報になる
- **ゴールデン価格帯は1500〜2980円**（ピーク1980〜2680円）
- **ゴールデンタイムは20時〜23時（JST）**。初動30件は全件この時間に配置する
- **投稿には3つの役割がある**
  - 評価取り（bait）… クリックと回遊を取る。売り込まない
  - 売上（cv）… 成約を取る。**必ず評価取りの直後に出す**
  - 送客（traffic）… 楽天市場へ送り、外部送客スコアを取る
- **ROOMは直前の行動リズムを強く引き継ぐ。** 評価取りで温めてから売上を出す
- **アルゴリズムは最初の30件に極端に重い比重を置く**
- **ルームは商品棚。** 高級品の隣に激安品を置くと購買心理が落ちる
- **NG行動6項目**（ジャンル散乱／買い理由0の投稿／売れない価格帯／棚の破壊／
  時間外投稿／AI最適化非対応）は `src/guard/ngcheck.js` が自動検査する
