# 引き継ぎ資料 — 楽天ROOM運用エンジン

このドキュメントは、クラウドセッションからローカル環境へ作業を移すためのものです。
システムの使い方は `README.md`、この文書は **「いま何がどこまで出来ていて、次に何を確かめるべきか」** を扱います。

---

## 1. 結論: ローカルに移すべき

理由は4つ。どれも運用上の実害に直結します。

**1) 定点観測データが消える**
このエンジンの売上速度は `data/snapshot-YYYY-MM-DD.json` の**日次差分**で成り立っています。
クラウドコンテナは一定時間で回収され、`data/` は `.gitignore` 対象（コミットされない）。
つまりクラウドで `collect` を回しても、翌日には比較対象が消えていて**売上速度が永久に未計測のまま**になります。
この機能はエンジンの重み22%を占めており、無効化すると別物になります。

**2) cron が必要**
`collect` は毎日、`now` はゴールデンタイム中5分おきに動かす前提です。
クラウドセッションは常駐プロセスではないので、この役割を担えません。

**3) 楽天アプリIDの置き場所**
`.env` はコミットされません。クラウドで使うには毎セッション入力し直すことになります。

**4) 投稿の実行が手元で起きる**
最後の貼り付け作業は、あなたの手元の端末で行います。台本が同じ端末に出るのが自然です。

### 逆に、クラウドに残す意味があるもの
ありません。ローカルでも Claude Code は同じように使えます。**開発も運用もローカルに一本化してください。**
唯一の例外は「複数台から触りたい」場合ですが、その場合は常時起動の小さなVPSに置くのが正解で、
このチャット環境ではありません。

## 3. 引き継ぎ手順

```bash
# 1. クローン（既にあるならフェッチ）
git clone https://github.com/longcape/claudeamazon.git
cd claudeamazon
git checkout claude/rakuten-room-automation-8c13zi

# 2. Node.js 18 以上を確認（依存パッケージは無いので npm install は不要）
node -v

# 3. 楽天アプリIDを設定
cd rakuten-room
cp .env.example .env
#   RAKUTEN_APP_ID=        ← https://webservice.rakuten.co.jp/ で即時発行

# 5. 設定と接続の確認
node bin/room.js doctor
```

`doctor` で「楽天API 応答あり」まで出れば引き継ぎ完了です。

## 4. ローカルで最初に確認すべきこと（優先順）

実APIに繋いだ直後、この順で潰してください。ここを飛ばすと後で原因が分からなくなります。

### ① ジャンルIDが実在するか — 最優先

`config/strategy.json` に入っている以下は**サンプル値**で、実在確認をしていません。

```
rootGenreId:      100938（インテリア・寝具・収納）… 確度は高いが要確認
relatedGenreIds:  100804, 558929               … 特に 558929 は確度が低い
```

```bash
node bin/room.js genre 0        # 大ジャンル一覧を出す
node bin/room.js genre 100938   # 子ジャンルを掘る
```

**そもそもこのジャンルはサンプルです。ご自身が実際に扱う商材のジャンルに置き換えてください。**
`genre.subThemes` のキーワードも全部書き換える前提です。ここが本番の質を決めます。

### ② レスポンスが想定どおりか点検する

```bash
node bin/room.js probe                    # strategy.json の先頭キーワードで点検
node bin/room.js probe "キッチン 収納"     # キーワードを指定する場合
```

30件を取得して、各フィールドが何%埋まっているかを出します。
「動いてはいるが全商品の作り込み度が0」のような**静かな故障**を最初に見つけるためのコマンドです。

```
● レスポンスの充足率
  ○ 商品説明         97%  (29/30)
  ○ アフィリ報酬率  100%  (30/30)
  ...
```

`×` や `△` が出た項目は、そのまま放置するとスコアが壊れます。影響も併せて表示されます。

| 欠損する項目 | 影響 |
| --- | --- |
| 商品説明 | 作り込み度が全商品0になる |
| **アフィリ報酬率** | **広告加熱度が機能しない（最重要）** |
| ポイント倍率 | ポイント評価が効かない |
| レビュー件数・平均 | ハードフィルタを誰も通らない |
| アフィリリンク | `RAKUTEN_AFFILIATE_ID` が未設定か不正 |

欠損が出た場合は `src/rakuten/ichiba.js` の `searchItems` が渡しているパラメータを疑ってください。
特に `field` は `0`（全情報取得）にしてあります。`1` は「一部の情報のみ」の指定で、
商品説明や報酬率が落ちます。

**併せて出る2つの数字も見てください。**

- **ハードフィルタの通過率** — 0件なら、そのキーワードでは候補が集まりません。商材とのズレを疑う
- **アフィリ報酬率の分布（最小/中央/最大）** — `config/strategy.json` の
  `adHeat.affiliateRateBase` / `affiliateRateHot` を、この実測幅に合わせてください。
  既定は 2%〜8% ですが、ジャンルによって相場が違います。**ここがズレていると広告加熱度が
  全商品ほぼ同じ値になり、選定が効きません。**

### ③ レート制限に引っかからないか

`collect` は現在の設定でおよそ **(サブテーマ5 × キーワード4〜5) × ソート3 × 2ページ ＋ ランキング6 ≒ 150リクエスト**。
1リクエスト1.1秒間隔なので **約3分**かかります。

```bash
node bin/room.js collect
```

`429 を返し続けています` が出る場合は `src/rakuten/client.js` の `MIN_INTERVAL_MS` を
1100 → 1500 あたりに上げてください。

### ④ 実データでのスコア分布を見る

初回 `collect` のあと:

```bash
node bin/room.js launch --nocheck
```

**「スコア基準を 0.62 → ○○ に緩めました」の緩和幅**を見てください。

- 0.58 以上で収まる → 妥当。そのまま
- 0.50 を割る → 候補の質が足りない。`subThemes` のキーワードを増やす
- 逆に一度も緩和されない → 基準が緩すぎる可能性。`launch.minSelectionScore` を上げてもよい

なお**初回は必ず緩みます**（売上速度が全件未計測のため）。判断は3日目以降に。

### ⑤ 紹介文が商品と噛み合っているか

`out/plan-launch-*.md` を開いて、10件ほど読んでください。
「悩み → 変化」が商品とズレていたら、`config/copy-lexicon.json` の `featureRules` に
その商材特有の語を足します。**ここを厚くするのが投稿の質に最も効きます。**

## 5. 最初の2週間の運用

| 日 | やること |
| --- | --- |
| 1日目 | §3 セットアップ → `room probe` → §4 ①〜③ を潰す → `collect` |
| 2日目 | `collect`（ここで初めて売上速度が出る）→ §4 ④⑤ |
| 3日目 | `collect` → `launch` で初動30件を確定 → 投稿開始 |
| 4〜6日目 | 30件を1日10件ずつ消化。`done` で消し込み |
| 7日目 | `record` で実績を入れる → `report` で代理指標を見る |
| 8日目〜 | `daily` で通常運用へ。実績が6件を超えると学習が効き始める |

**初動30件は3日目以降に組んでください。** アルゴリズムが最初の30件に極端に重い比重を置く以上、
売上速度が未計測のまま組むのが一番もったいない選択です。1〜2日目は `collect` を回すだけで構いません。

cron（macOS / Linux）:

```cron
0 3 * * *        cd ~/claudeamazon/rakuten-room && /usr/local/bin/node bin/room.js daily
*/5 20-23 * * *  cd ~/claudeamazon/rakuten-room && /usr/local/bin/node bin/room.js now --adapter=webhook
```

`which node` でパスを確認して置き換えてください。cron は PATH を継承しません。

## 6. データの扱い（重要）

`data/` は `.gitignore` されています。**これは意図的です**（アフィリエイトIDを含むURLや実績が
公開リポジトリに載るのを防ぐため）。ただし裏を返すと、**消したら復旧できません。**

| ファイル | 失うと何が起きるか |
| --- | --- |
| `snapshot-*.json` | 売上速度が振り出しに戻る（再蓄積に数日） |
| `history.json` | **一度投稿した商品が再び選ばれる**（同じ商品の重複投稿） |
| `results.json` | 実績学習がリセットされる |
| `plan-*.json` | 投稿済みフラグが消え、どこまで出したか分からなくなる |

対策として、`data/` を定期的にリポジトリ外へコピーしてください。

```bash
# 例: 週1でバックアップ
cp -r ~/claudeamazon/rakuten-room/data ~/backup/room-data-$(date +%Y%m%d)
```

プライベートリポジトリで運用するなら、`.gitignore` から `data/*.json` を外して
コミットするのが最も安全です（複数台で運用する場合も同じ）。

## 7. 設計上の判断メモ

「なぜそうなっているか」を残します。触っていい場所と、壊れやすい場所の区別です。

### 気軽に触ってよい

| 場所 | 内容 |
| --- | --- |
| `config/strategy.json` | 全パラメータ。ジャンル・価格帯・時間帯・比率・重み。**基本ここだけで調整が完結します** |
| `config/copy-lexicon.json` | 紹介文の語彙。足すほど文が具体的になる |
| `config/trend-words.json` の `rising` | 上昇ワード。`room trend` の提案から手で昇格させる |

### 触ると壊れやすい

**`src/plan/sequence.js` の `arrange()`**
「売上投稿は必ず評価取りの直後」を構造的に保証している箇所です。
当初はパターン列（`["bait","cv","bait",...]`）を頭から消費する方式でしたが、
**末尾で評価取りが尽きて売上が連続する事故**が起きたため、
先に〈評価取り＋売上〉のペアを確定させ、隙間に単発と送客を配る方式に作り直しました。
ここを「パターン通りに並べればいい」と単純化すると、その事故が戻ります。
`test/pipeline.test.js` の「売上投稿は必ず評価取り投稿の直後に来る」がこれを守っています。

**`src/plan/shelf.js` の `smooth()`**
価格段差を均しますが、**同じ役割の商品どうししか入れ替えません**。
役割をまたいで入れ替えると上記のペアが壊れます。

**`src/pipeline/select.js` の枠埋め**
1ショップ3商品上限があるため、30件出すには最低10ショップぶんの候補が要ります。
スコア基準の自動緩和は「件数」だけでなく「ショップ数」も見て判断しています。
件数だけで判定すると、候補は足りているのに枠が埋まらない状態になります。

**`src/copy/generate.js` の `extractFeature()`**
商品名での一致を説明文より**必ず優先**します。
保存容器の説明文に「伸縮」と書いてあるだけで伸縮商品として売ってしまい、
文が商品と噛み合わなくなる事故を防ぐためです。

### 意図的にそうしている

- **売上速度が計測できない商品は0点ではなく0.35**（中庸）。データが無いことを不利にしすぎないため
- **実績学習は6件たまるまで動かない**。少ないサンプルで重みを動かすと、たまたま当たった1件に引きずられる
- **`room trend` の上昇ワードは自動で `rising` に入らない**。誤検出が紹介文に混ざるのを防ぐため手動昇格

## 8. 未着手・今後の候補

優先度順。どれも現状の運用を止めるものではありません。

1. **LLMによる紹介文の自然化の実地確認** — 実装済みだが一度も実行していない。`ANTHROPIC_API_KEY` を入れて `launch` を回し、出力を目で確認する。3要素が保たれない出力は自動で破棄する作りにはなっている
2. **webhook アダプタの実地確認** — Discord / Slack の Incoming Webhook URL で `now --adapter=webhook` を試す
3. **楽天ROOM側の実績取り込みの半自動化** — 現状 `record` は手入力。楽天アフィリエイトのレポートCSVをパースする口を足せば手間が減る
4. **複数ジャンルの並行運用** — `ROOM_DATA_DIR` で保存先を分けられるので、設定ファイルを分ければ実現可能。ただし**1ジャンル集中の原則に反する**ので、1つ目が軌道に乗ってから
5. **画像作り込み度の精度向上** — 現状は画像枚数と説明文の長さから推定している。商品ページのHTMLを取得すれば精度は上がるが、スクレイピングになるので規約面で要検討

## 10. このセッションで直した既知の落とし穴

同じ轍を踏まないよう記録します。実データに触ると似た問題がまた出ます。

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| 売上投稿が末尾で連続した | パターン列を頭から消費する方式 | ペア確定方式に作り直し（§7） |
| 90商品が10商品に潰れた | 重複排除の指紋が商品名の先頭14文字だけ | 商品名の数値（段数・本数）も指紋に混ぜた |
| 30枠のうち21枠しか埋まらない | 1ショップ3商品上限 × 候補が7ショップ分しかない | 原因を名指しで警告するようにした |
| 日中の投稿枠が空振りした | ペアが1枠のスロットに入らず break していた | 先読みして単発投稿を回すようにした |
| 20:00より前に投稿が入った | ゆらぎがゴールデンタイムの外へはみ出した | 内側にクランプ |
| 保存容器が「伸縮」商品として売られた | 説明文の宣伝文句を拾っていた | 商品名の一致を優先（§7） |
| （実データで再発しうる）商品説明・報酬率が空 | `field=1` は一部の情報のみ返す指定 | `field: 0`（全情報）に修正済み。§4② で必ず確認 |
